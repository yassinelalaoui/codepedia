# UI Mount Points Contract — Section Rail Delta

## Purpose

This feature adds exactly one new container element to the shared HTML layout
defined by `specs/016-wiki-web-interface/contracts/ui-mount-points.md`. It
changes nothing else — `#wiki-search-root`, `#wiki-chat-root`, the stylesheet
link, the classic (non-`module`) script tag and its end-of-body placement, the
single page-relative `search-index.json` fetch, and every degradation and
non-collision guarantee in 016 are all unaffected and unchanged.

016 enumerates "two empty container elements, present on every page". That count
becomes three; the *invariant behind it* — that every container lives in the
shared layout, so the bundle never has to special-case which kind of page it is
running on — is preserved exactly.

## `#wiki-toc-root` — new

`layout.html.jinja` gains a third empty container:

```html
<div id="wiki-toc-root"></div>
```

Present on **every** page (home, module, diagram), unconditionally — including
pages whose section rail is empty. A page-conditional container would have
forced the bundle to special-case page kinds, which is what 016's
always-present rule exists to prevent.

## Bundle responsibility

The bundle mounts `TocHighlighter` into `#wiki-toc-root`. `main.tsx`'s existing
`mount()` helper already returns silently when a container is absent, so a page
generated by an older `doc_generator` degrades to no highlighting rather than an
error.

`TocHighlighter` is **headless**: it renders `null` and owns no markup. Its only
effect is to toggle an `active` class on links inside the server-rendered
`.page-toc` rail, driven by an `IntersectionObserver` over the page's headings.

## What the rail is, and why it is not React-rendered

The "On this page" rail itself is emitted server-side by `layout.html.jinja`
from `page_toc`, which `html_render.py` derives from Python-Markdown's
`toc_tokens` at render time (never persisted — `manifest_store` is untouched).

This follows the sidebar's module list, which is likewise plain Jinja with a
server-computed `active` class, and it keeps three properties 016 cares about:

- The rail navigates with **no JavaScript at all**, and over `file://`, which is
  the degradation mode 016 is written around.
- There is no empty-then-populated flash on every page load for what is
  navigation chrome.
- Heading anchors have exactly one source of truth — Python-Markdown's `toc`
  extension — rather than a second slug convention on the client that could
  silently drift from it.

Consequently the rail is **not** data injected through
`window.__WIKI_UI_CONFIG__`. That object continues to carry only
`searchIndexHref`, preserving 016's "Python tells JS where to fetch from"
shape rather than shipping per-page content through it.

## Non-collision

`doc_generator` never emits `id="wiki-toc-root"` anywhere else on a page, and
`TocHighlighter` modifies only `class` attributes on `a.page-toc-link` elements
inside `.page-toc`. It does not touch `pre.mermaid` elements or the Mermaid
initialization script (013), and it does not touch page content.
