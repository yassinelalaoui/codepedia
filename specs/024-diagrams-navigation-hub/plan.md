# Implementation Plan: Diagrams Navigation Hub

**Branch**: `024-diagrams-navigation-hub` | **Date**: 2026-08-18 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/024-diagrams-navigation-hub/spec.md`

**Note on the planning prompt**: the natural-language description supplied to
`/speckit-plan` for this run described the target as a React+TS `frontend/`
app with no tab/navigation system, needing a navbar "injected into the shared
page template of `doc_generator`" and diagrams "produced by 8.1/8.2/8.3"
framed as work still to be added. Inspecting the actual codebase shows this
is only partly accurate and conflicts with `spec.md`'s already-recorded,
clarified Input: the generated wiki's shared page template
(`src/doc_generator/templates/layout.html.jinja`) already renders a
persistent `<nav>` with a Home link on every page; `frontend/` only supplies
two independently mounted widgets (search, chat) into `#wiki-search-root`/
`#wiki-chat-root` on that same server-rendered page — it owns no routing or
navigation. The class diagram (8.1, `021-repository-class-diagram`), the
per-entry-point sequence diagrams (8.2, `022-entry-point-sequence-diagram`),
and the use-case diagram (8.3, `023-repository-use-case-diagram`) are already
implemented and generating pages today (confirmed via `generator.py`,
`class_diagram.py`, `entry_point_diagram.py`, `use_case_diagram.py`), not
future work. This plan follows `spec.md`'s Input and Clarifications (the
authoritative, already-corrected source) rather than the stale framing in the
planning prompt: it extends the existing `nav` in `layout.html.jinja` with
one new "Diagrams" link, and adds one new page generated by `doc_generator`
that aggregates links already-existing diagram-generating code produces.

## Summary

Add one new, always-present "Diagrams" page to the generated wiki
(`doc_generator`) that lists every diagram the wiki currently produces — the
repository class diagram (021), every entry point's sequence diagram (022),
the repository use-case diagram (023), and every module's dependency diagram
(013) — grouped by category, each openable in one click, and never listing a
module's text-documentation page. Add a second link, "Diagrams", to the
persistent `<nav>` already rendered on every generated page
(`layout.html.jinja`), next to the existing Home link, so the new page is
reachable in exactly one click from anywhere in the wiki (FR-002). This
feature introduces no new diagram type and does not change how any existing
diagram is generated or what it contains — it only reads the page
identities/links those four generators already produce (or would produce)
and reuses the existing incremental-regeneration manifest
(`DocPageManifestStore`, `impact.py`) so the page stays current after an
incremental re-index, the same way the Home page already does.

## Technical Context

**Language/Version**: Python 3.11+, extending the existing `doc_generator`
package only. `frontend/` (React+TS) is unaffected — the nav lives in the
server-rendered Jinja layout, not in the React bundle (see "Note on the
planning prompt" above).

**Primary Dependencies**: Existing `doc_generator`, `links.py`, `generator.py`,
`impact.py`, `manifest_store.py`, `writer.py`, `html_render.py`, and their
existing `Jinja2`/`Markdown` rendering pipeline — reused unmodified in kind;
no new Python dependency; no new client-side asset (no JavaScript is needed
for a static list of links, unlike the search/chat widgets).

**Storage**: No new persistence. The new page's manifest entry reuses the
existing `DocPageManifestStore` (012, SQLite) exactly like every other page
kind. The page's *content* (which diagrams currently exist) is recomputed
from the already-loaded `RepositoryBundle`/`DependencyGraph` and the diagram
page identities `generateClassDiagramPage`/`generateUseCaseDiagramPage`/
`generateEntryPointSequenceDiagramPages`/the per-module diagram loop already
compute each run — never separately cached.

**Testing**: pytest, extending the existing `tests/integration/
test_doc_generator_links.py`-style and `test_doc_generator_home_overview.py`-
style suites: a fixture repository with at least one module, one class, and
one identifiable entry point produces a Diagrams page listing exactly one
class-diagram entry, one use-case-diagram entry, one sequence-diagram entry
per entry point, and one dependency-diagram entry per module, with no
module-documentation entries (spec Acceptance Scenario 2); the Home page
(and every other page) links to the Diagrams page (FR-002); a repository
with no classes and no entry points produces a Diagrams page that omits
those two categories entirely, not empty placeholders (Acceptance Scenario
5); a repository producing zero diagrams still produces a valid, openable,
empty Diagrams page (Edge Case); incremental regeneration correctly
refreshes the Diagrams page when the diagram set changes (add/remove a
module, add/remove an entry point, gain/lose the repository's last class) —
no headless-browser rendering test, consistent with 013/021/022/023.

**Target Platform**: Any standard web browser opening the generated
documentation from local files or a static host; generation runs on
Windows/macOS/Linux like the rest of the toolchain.

**Project Type**: Extension of the existing internal documentation-generation
library (`doc_generator`, feature 012). No new top-level package, no changes
outside `doc_generator` — in particular, no changes to `frontend/`.

**Performance Goals**: A single linear pass over already-computed page
identities (module list, class-diagram/use-case-diagram existence,
entry-point list) — O(diagram count), no new graph traversal or source
re-parse; expected to add no perceptible overhead, consistent with
013/021/022/023's own selection steps.

**Constraints**: Zero network requests at view time (a plain static page,
same as every other generated page); read-only analysis only, no new writes
outside the existing `outputRoot`; the page must never list a module's
text-documentation page (FR-004); a diagram category with zero entries must
be omitted entirely, never rendered as an empty/broken placeholder (FR-006).

**Scale/Scope**: One new page (not one per module, not one per diagram) plus
a one-line addition to the single shared nav template — its size grows with
total diagram count across the whole repository, same growth profile as the
Home page's module list.

**Structure Decision**: Keep this feature entirely inside the existing
`doc_generator` package, mirroring how 013/021/022/023 each extended it —
zero changes outside `doc_generator`, and in particular zero changes to
`frontend/`. Unlike 021/022/023 (each a new *diagram* type with its own
selection + Mermaid-rendering stage), this feature introduces no selection
or rendering stage of its own: it is a navigation/aggregation page over page
identities those features' generator methods already compute each run, so
it only touches `links.py`/`generator.py`/`impact.py`/`models.py`/
`html_render.py` plus one new markdown template and one shared-layout edit —
no new `*_diagram.py` module, no new Mermaid source.
