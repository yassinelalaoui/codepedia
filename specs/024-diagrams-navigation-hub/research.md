# Research: Diagrams Navigation Hub

## Decision 0 — Ground this plan in `spec.md`'s Input, not the raw planning-prompt text

**Decision**: Treat `spec.md`'s recorded Input and Clarifications (already
reconciled with this codebase on 2026-08-18) as authoritative over the
natural-language description supplied to this `/speckit-plan` invocation.

**Rationale**: The supplied prompt claimed `frontend/` (React+TS) "has no
tab/navigation system" and asked for a navbar "injected into the shared page
template of `doc_generator`" plus diagrams "produced by 8.1/8.2/8.3" framed
as work still to be added. Direct inspection shows: (a)
`src/doc_generator/templates/layout.html.jinja` already renders a persistent
`<nav>` with a Home link on every generated page — navigation is not absent,
only incomplete (one link); (b) `frontend/src` only builds two independently
mounted widgets (search, chat) injected into `#wiki-search-root`/
`#wiki-chat-root` on that same server-rendered page — it has no router and
owns no navigation, so "inject a navbar into the shared page template of
`doc_generator`" is already correct in spirit but the "no navigation exists"
framing is not; (c) `class_diagram.py` (021, "8.1"),
`entry_point_diagram.py`+the sequence-diagram generation method (022,
"8.2"), and `use_case_diagram.py` (023, "8.3") are already implemented and
generating pages today, confirmed via `generator.py`'s
`generateClassDiagramPage`/`generateEntryPointSequenceDiagramPages`/
`generateUseCaseDiagramPage` and the project's own commit history. `spec.md`
already reflects this reality accurately (its Input and "Note" section name
021/022/023/013 as already-existing prior features this one only aggregates
links to), so this plan follows `spec.md`, not the stale prompt framing.

**Alternatives considered**: Planning literally against the supplied
prompt's framing (treat 8.1/8.2/8.3 as not-yet-built, scope a React-side
router into `frontend/`) — rejected: it would duplicate already-shipped
functionality, contradict the already-clarified spec, and misplace the nav
in a subsystem (`frontend/`) that does not own page routing in this
project's actual architecture.

## Decision 1 — The Diagrams page is a navigation/aggregation page, not a new diagram type

**Decision**: Add one new `PageKind`, `"diagrams-index"`, generated by a new
`DocGenerator.generateDiagramsIndexPage()` method. Unlike 021/022/023, this
feature introduces no selection module (`*_diagram.py`) and no new Mermaid
rendering function — it only reads the page identity (id, title/label,
output path) that `generateClassDiagramPage`, `generateUseCaseDiagramPage`,
`generateEntryPointSequenceDiagramPages`, and the existing per-module
dependency-diagram loop already compute, and turns those into a grouped list
of links via one new markdown template, `diagrams_index.md.jinja`.

**Rationale**: Directly matches the spec's own framing ("This feature
surfaces and links to diagrams already produced by prior features... It
introduces no new diagram type of its own — only a dedicated,
always-reachable page that aggregates links"). Reusing the exact page
identity each existing generator method already computes (the same
`module_key`/`slug`/output-path computation `generateOverviewPage` already
performs for its own per-module "dependencies" link) avoids a second,
possibly-drifting notion of "which diagrams exist" — there is exactly one
place, per diagram kind, that decides a diagram page's id/output path
(`links.py`), and this feature only reads it.

**Alternatives considered**: Re-deriving "which diagrams exist" by scanning
the manifest store (`DocPageManifestStore.list_entries`) after the fact —
rejected: on a non-incremental (from-scratch) run, or on the very first
generation, relying on manifest state read back from disk introduces an
ordering dependency (the index page would need to run strictly after every
other page's `write_page` call) and would show last-run's diagram set rather
than this run's, which is exactly the staleness problem `impact.py` already
solves for the Home page. Instead, this page follows the Home page's own
pattern: recomputed from already-in-memory identities, written using the
same target-page-id gating as every other page.

## Decision 2 — Page is always generated, never omitted, even with zero diagrams

**Decision**: `generateDiagramsIndexPage()` always returns a `DocPage`
(never `None`), unlike `generateClassDiagramPage()`/
`generateUseCaseDiagramPage()`, which return `None` when their respective
diagram would be empty. `diagrams_index.md.jinja` renders an explicit "no
diagrams yet" message when every category is empty rather than an empty or
broken page.

**Rationale**: FR-002 requires the "Diagrams" nav link to be present and
functional "regardless of which page the user is currently viewing", and the
spec's Edge Case is explicit: "What happens when the analyzed repository
produces zero diagrams of any kind? The Diagrams page still opens and shows
an empty list, never a broken page." A conditionally-present target page
would leave the nav link either absent (contradicting FR-002, which never
makes the link conditional) or dangling (a broken link), neither acceptable.
This mirrors how the Home page itself is unconditionally generated every run
regardless of repository content.

**Alternatives considered**: Omitting the nav link itself when the page
would be empty — rejected: FR-002 requires the link "on every page... with
exactly one user action, regardless of which page the user is currently
viewing," with no carve-out for an empty-repository case; the spec's own
Edge Case explicitly calls for the page (not the link) to handle emptiness.

## Decision 3 — Nav link lives in the single shared `layout.html.jinja`, computed the same way as the existing Home link

**Decision**: `html_render.render_page_html` gains one new computed href,
`diagrams_href`, built via the same `relative_output_link(from_output_path=
output_path_html, to_output_path=<diagrams index output path>)` call already
used for `home_href`, and passes it to `layout.html.jinja`. The template
gains one more `<a>` inside the existing `<nav>` element, next to Home.

**Rationale**: `layout.html.jinja` is the one page template every generated
page (home, module, diagram, class-diagram, sequence-diagram,
use-case-diagram, and now diagrams-index) already renders through via
`render_page_html` — it is the only place that can satisfy FR-002's "every
page" requirement in one change. Reusing the exact `relative_output_path`
mechanism already used for `home_href` keeps the two nav links symmetric
(both fixed-target, relative-path-computed hrefs) and requires no new
linking primitive.

**Alternatives considered**: Injecting the nav link client-side via
`wiki-ui.js` (the same bundle that mounts the search/chat widgets) —
rejected: adds a JavaScript/client-side-assembly dependency for what is a
one-line, static, server-known link; would flash-missing on slow script
loads; and contradicts Constitution 2.6 (minimal infrastructure) by adding
complexity a template edit already avoids.

## Decision 4 — Dependency-diagram catalog entries computed as lightweight identity links, not full diagram rebuilds

**Decision**: The Diagrams page's per-module dependency-diagram entries are
computed directly from `RepositoryBundle.files` (module name +
`sourceFileId` → `links.page_slug` → `links.diagram_output_paths` →
`links.diagram_page_id`), exactly the same computation
`generateOverviewPage` already performs to build each module's
"dependencies" link — not by calling `build_module_diagram` /
`generateDependencyDiagramPage` (which builds the full `DiagramExport` and
Mermaid source) just to learn a link's id/label/path.

**Rationale**: The Diagrams page only needs to *identify* each
dependency-diagram page (module name, its fixed output path) to link to it —
it does not render or embed the diagram itself. Reusing the Home page's
already-established, cheap identity computation avoids a second, more
expensive code path (full diagram export construction) purely to produce a
link, and keeps this feature's added cost at O(module count) with no graph
traversal beyond what `generateOverviewPage` already pays each run.

**Alternatives considered**: Reusing `generateOverviewPage`'s internal
`module_entries` list directly (share state between the two page methods) —
rejected: the two pages are not always regenerated in the same call (the
Diagrams page's regeneration trigger, Decision 6, is close to but not always
identical to the Home page's), and every existing page-generation method in
this codebase (`generateClassDiagramPage`, `generateUseCaseDiagramPage`,
`generateEntryPointSequenceDiagramPages`) is independently callable/
testable without depending on another page method's internals; a small,
shared private helper (e.g. `_dependency_diagram_links(modules)`) reused by
both `generateOverviewPage` and `generateDiagramsIndexPage` keeps that
same independence while avoiding duplicated logic.

## Decision 5 — Grouping and per-entry labeling for FR-008

**Decision**: `diagrams_index.md.jinja` renders up to four sections, in a
fixed order — Class diagram, Use-case diagram, Entry point sequence
diagrams, Module dependency diagrams — each present only when it has at
least one entry (Decision 2 covers the all-empty case). Each entry's label
identifies what it links to using the same label text each source generator
already uses elsewhere: `"Repository class diagram"` / `"Repository
use-case diagram"` (matching `generateOverviewPage`'s existing link labels),
each sequence-diagram entry's own `DocPage.title` (022's actual
per-entry-point page title, `f"{entry_point.name} — Call sequence"` —
verified against `generateEntryPointSequenceDiagramPages` in
`generator.py`, not the `Module[.Class].name` format used internally for
Mermaid participant labels), and `f"{module.name} dependencies"` (matching
`generateOverviewPage`'s existing per-module diagram-link label).

**Rationale**: Directly satisfies FR-008 ("Each entry... MUST clearly
identify what diagram it links to... so a user can choose the right one
without opening it first") using label text this codebase has already
established elsewhere, rather than inventing new wording — keeps the
generated wiki textually consistent between the Home page's existing links
and this page's links to the same targets. Fixed section order (rather than
encounter order) makes repeated generation runs produce a stable page for
the same repository state, consistent with 021/022/023's own determinism
requirements for their diagrams.

**Alternatives considered**: A single flat list with no grouping — rejected:
the spec's Edge Case ("must remain a single, flat, directly clickable
list — the user must never be required to drill down module by module")
constrains *navigation depth* (no drill-down), not visual grouping; FR-008
separately requires each entry to identify its own category, which a
labeled section heading satisfies more directly than repeating the category
in every entry's own text.

## Decision 6 — Incremental regeneration: new `requiresDiagramsIndexRegeneration` flag on `RegenerationImpactSet`

**Decision**: Extend `RegenerationImpactSet` with a new field,
`requiresDiagramsIndexRegeneration: bool`, computed in
`compute_regeneration_impact` as true whenever any of the following differ
from the previous manifest snapshot: the current set of module page ids
(same condition `requiresHomePageRegeneration` already uses), the current
set of sequence-diagram page ids (022's entry-point set), whether a
class-diagram page currently exists, or whether a use-case-diagram page
currently exists. In `generateRepositoryDocumentation`, when this flag is
true (or on a full/non-incremental run), `links.diagrams_index_page_id()` is
added to `target_page_ids` alongside `HOME_PAGE_ID`.

**Rationale**: FR-007/SC-003 require the Diagrams page to "reflect exactly
the current set of diagrams" after an incremental re-index. The existing
`requiresHomePageRegeneration` flag only tracks the module-page set — it
does not flip when a repository gains/loses its only class or its only
entry point (Acceptance Scenario 5 / Edge Case: a repository with no classes
and no entry points must show only the categories that exist). A new,
narrowly-scoped field keeps this an additive, backward-compatible extension
to `RegenerationImpactSet` (existing callers/tests of
`requiresHomePageRegeneration` are unaffected) while giving the Diagrams
page a trigger that actually covers every category it displays.

**Alternatives considered**: Reusing/broadening `requiresHomePageRegeneration`
itself to also cover class/use-case/entry-point existence flips — rejected:
that field is already asserted on by existing tests
(`test_doc_generator_home_overview.py`-style) for its current, narrower
meaning (module-page-set changes only); broadening its semantics risks
silently changing when the Home page itself regenerates, which is out of
this feature's scope (the Home page's own class-diagram/use-case-diagram
links can legitimately lag by one triggering change today, a pre-existing
characteristic this feature does not need to alter). Regenerating the
Diagrams page unconditionally on every run — rejected: defeats incremental
regeneration (Constitution 2.5) when nothing diagram-related changed.

## Decision 7 — No new external contract; document the page as a UI/content contract

**Decision**: This feature adds no new API, CLI flag, or externally callable
function beyond the one new `DocGenerator` method
(`generateDiagramsIndexPage`) and template. `contracts/
diagrams-index-page.md` documents that method's and the nav link's expected
behavior as a UI/content contract (what the rendered page must and must not
contain, per FR-001/FR-003/FR-004/FR-006), following the plan template's
guidance to document "the contract format appropriate for the project
type... UI contracts for applications" rather than an API schema.

**Rationale**: This is an internal documentation-generation library with no
public HTTP/CLI surface change; the only thing a consumer (a developer
reading the generated wiki) observes is the page's content and the nav
link's presence, so that is what the contract specifies — mirroring how
021/023 each wrote a contract for their own selection+rendering functions.

**Alternatives considered**: Skipping `contracts/` entirely as "purely
internal" — rejected: the generated wiki page is itself a
user-facing interface (the feature's entire purpose per FR-001/FR-002), so a
UI contract is the appropriate artifact, consistent with the plan template's
own guidance and with 021/023's precedent of writing one even though neither
exposes an HTTP API.
