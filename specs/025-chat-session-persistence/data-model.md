# Phase 1 Data Model: Chat Session Persistence

## Overview

Two new tables in the existing per-repository `repository-metadata.sqlite`
file (same file/schema as `repositories` / `source_files` / `symbols` /
`dependency_graphs` / `dependency_edges`, per `repository_metadata.sqlite_store`).
No new database file. Object mapping is the existing `chat.models.ChatSession`
/ `chat.models.ChatMessage` dataclasses (extended, not duplicated) — see
research.md Decisions 1–3.

## Entities

### ChatSession (`chat_sessions` table)

Maps to `chat.models.ChatSession`'s persisted subset: `id`, `createdAt`,
`lastActivityAt`. The dataclass's other fields (`vectorIndex`,
`embeddingEngine`, `llmEngine`, `topK`, `messages`) are runtime-only and are
never read from or written to this table — `messages` is populated
separately from `chat_messages` on load.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | The existing chat session id (`uuid4().hex`, generated by `SessionRegistry.create_session`, per 014). Stable across restarts by construction. |
| `created_at` | `TEXT NOT NULL` | ISO-8601 UTC, set once at creation, never updated. |
| `last_activity_at` | `TEXT NOT NULL` | ISO-8601 UTC, refreshed every time a message is appended to this session. |

Validation rules (mirroring `ChatMessage.__post_init__`'s existing style):
`id` must be non-empty; `created_at` / `last_activity_at` must be non-empty
ISO-8601 strings.

No `repository_id` column: per spec Assumptions, sessions are scoped per
repository the same way the rest of `repository-metadata.sqlite` already is
— by *which file* they live in (one file per repository under
`~/.repo-scanner/repos/<state_id>/repository-metadata.sqlite`), not by an
explicit foreign key. This matches how `repositories`/`source_files` are
scoped in the same file today.

### ChatMessage (`chat_messages` table)

Maps to `chat.models.ChatMessage` exactly as it exists today — no new
fields needed on the dataclass itself.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | New synthetic id for the row (e.g. `uuid4().hex`), not currently a `ChatMessage` field — needed as a stable per-message identity independent of ordering. Not exposed through the existing `ChatMessageView` API schema; internal to the store. |
| `session_id` | `TEXT NOT NULL` | `FOREIGN KEY -> chat_sessions(id) ON DELETE CASCADE` (mirrors the `ON DELETE CASCADE` pattern already used for `source_files` → `repositories`, `symbols` → `source_files`). |
| `role` | `TEXT NOT NULL` | `"user"` or `"assistant"`, from `ChatMessage.role`. |
| `content` | `TEXT NOT NULL` | From `ChatMessage.content`. |
| `cited_symbol_ids` | `TEXT NOT NULL` | JSON-encoded array (`json.dumps`), mirroring how `symbols.metadata` / `module_symbols.imports` already store lists as JSON text in this same file. Empty list persists as `"[]"`. |
| `cited_file_paths` | `TEXT NOT NULL` | JSON-encoded array, same convention as above. |
| `timestamp` | `TEXT NOT NULL` | From `ChatMessage.timestamp` (ISO-8601 UTC, set at message construction). |
| `sequence` | `INTEGER NOT NULL` | Monotonically increasing per-session insertion counter (e.g. `1, 2, 3, ...`), used as the tie-breaker when two messages share a `timestamp` (edge case in spec.md) so chronological order stays well-defined via `ORDER BY timestamp, sequence` rather than `timestamp` alone. |

Validation rules: reuses `ChatMessage.__post_init__`'s existing
normalization (non-empty `role`/`content`, deduped citation lists) — nothing
new to validate at the storage layer beyond what the dataclass already
enforces before a row is ever written.

Index: `CREATE INDEX IF NOT EXISTS idx_chat_messages_session_timestamp ON
chat_messages(session_id, timestamp)` — supports `load_messages(session_id)`
doing a single ordered range scan instead of a table scan, per FR-005 / SC-004.

## Relationships

```text
chat_sessions (1) ──< (many) chat_messages
     id                    session_id (FK, ON DELETE CASCADE)
```

A `ChatSession` has zero or more `ChatMessage`s, in chronological order
(`ORDER BY timestamp, sequence`). A `ChatMessage` belongs to exactly one
`ChatSession`. No relationship to `repositories`/`source_files`/`symbols` —
scoping is per-file, not per-row (see ChatSession section above).

## State / Lifecycle

- **Created**: `SessionRegistry.create_session()` → `chat.sqlite_store.create_session()`
  inserts one `chat_sessions` row with `created_at == last_activity_at == now`.
  No messages yet (spec.md edge case: a session with zero messages must still
  exist and be retrievable after a restart).
- **Appended to**: `ChatSession.ask()` inserts one `chat_messages` row per
  message (user, then assistant) and updates `chat_sessions.last_activity_at`.
  Append-only — no update/delete path for an existing message (spec.md
  Assumptions).
- **Read**: `chat.sqlite_store.load_session()` (row → `ChatSession` sans
  `messages`) + `load_messages()` (ordered rows → `tuple[ChatMessage, ...]`),
  combined by `SessionRegistry.get_session()` into one populated `ChatSession`.
- **No deletion/expiry path** — out of scope per spec.md Assumptions.
