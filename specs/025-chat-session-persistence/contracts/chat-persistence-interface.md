# Chat Persistence Interface Contract

## Purpose

Define the storage-facing operations `chat/sqlite_store.py` exposes to
`chat_api.SessionRegistry` (and to `chat.ChatSession` itself, for
appending) to make a session's history durable across process restarts,
operating on the schema defined in `chat-persistence-schema.md` and
returning/consuming the existing `chat.models.ChatSession` /
`chat.models.ChatMessage` objects directly (no separate DTOs — see
research.md Decision 2).

## Core operations

### `create_session`

Inputs:
- database path (the repository's `repository-metadata.sqlite`)
- session id (already generated by the caller, per the existing
  `SessionRegistry.create_session` id scheme)

Expected behavior:
- Inserts one `chat_sessions` row with `created_at == last_activity_at == now`.
- Fails loudly (raises) rather than silently overwriting on a colliding id —
  ids are expected to be unique by construction (uuid4).

### `touch_session`

Inputs:
- database path
- session id

Expected behavior:
- Updates `chat_sessions.last_activity_at` to now for that id.
- Called as part of `append_message`, never on its own by external callers.

### `append_message`

Inputs:
- database path
- session id
- one `chat.models.ChatMessage`

Expected behavior:
- Inserts exactly one `chat_messages` row for that message, with the next
  `sequence` value for that session.
- Also refreshes the owning session's `last_activity_at` (see `touch_session`).
- Never reads, rewrites, or re-serializes any other message in the session —
  this is the operation FR-004 / SC-003 constrain to stay O(1).
- Raises if `session_id` does not reference an existing `chat_sessions` row
  (the caller is expected to have created the session first).

### `load_session`

Inputs:
- database path
- session id

Expected behavior:
- Returns a `chat.models.ChatSession` populated with `id`, `createdAt`,
  `lastActivityAt`, and an **empty** `messages` list — callers combine this
  with `load_messages` themselves (kept separate so a caller that only needs
  to check existence, e.g. for a 404 decision, doesn't pay for loading the
  full history).
- Raises `KeyError` (mirroring `repository_metadata.sqlite_store.load_repository`'s
  existing convention) when no such session id exists — this is what lets
  `SessionRegistry` distinguish "unknown session" (FR-008) from "session
  exists, no messages yet."

### `load_messages`

Inputs:
- database path
- session id

Expected behavior:
- Returns `tuple[chat.models.ChatMessage, ...]` for that session, ordered by
  `(timestamp, sequence)`, in a single query (FR-005 / SC-004).
- Returns an empty tuple (not an error) for a session that exists but has no
  messages yet (spec.md edge case).
- Does not raise for an unknown session id — returning an empty tuple would
  be indistinguishable from "no messages yet," so callers that need to
  distinguish "unknown session" must call `load_session` first (matching how
  `SessionRegistry.get_session` already needs to raise `SessionNotFoundError`
  for an unknown id regardless of message count).

## Non-goals

- No `delete_session` / `delete_message` / `list_sessions` operations — out
  of scope per spec.md Assumptions (append-only, no session
  listing/deletion/expiry in this feature).
- No pagination on `load_messages` — SC-004 requires the full history in one
  request; splitting it across requests would violate that success criterion.
