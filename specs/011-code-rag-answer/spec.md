# Feature Specification: Local Code RAG Answering

## Overview

Build a local retrieval-augmented generation pipeline that answers a natural
language question about the indexed codebase. The pipeline must turn the
developer's question into a local semantic query, retrieve the most relevant
code fragments and existing summaries from the local index, assemble that
evidence into a prompt, and return a natural-language answer generated by the
local model.

The answer must explicitly cite the files and symbols used to justify the
response. The pipeline must remain fully local at every step and must never
send code data to any service other than the configured local model.

## Goals

- Answer repository questions with relevant local code evidence.
- Retrieve the most useful source fragments and summaries for the question.
- Ground every answer in citations to files and symbols from the repository.
- Keep the full question-to-answer flow local and offline-friendly.
- Refuse to hide or mask any failure to use the local model or local index.

## Non-Goals

- Replacing the existing symbol extraction, dependency analysis, or embedding
  pipelines.
- Generating answers from cloud-hosted models or external search services.
- Editing source files or repository metadata during question answering.
- Providing a general-purpose internet-enabled coding assistant.
- Guaranteeing an answer for questions that have no supporting evidence in the
  indexed repository.

## User Stories

### US1 - Ask a question about the indexed codebase

As a developer, I want to ask a natural-language question about the indexed
repository so that I can quickly understand where a behavior is implemented and
which code is responsible for it.

Acceptance criteria:

- A user question produces a natural-language answer.
- The answer is grounded in the indexed repository content.
- The answer references the files and symbols that support it.
- The answer is understandable without reading raw search results.

### US2 - Retrieve local evidence before answering

As a developer, I want the system to retrieve the most relevant local code
fragments and summaries before it answers so that the response reflects the
actual repository state.

Acceptance criteria:

- The pipeline uses the question to find relevant local fragments.
- The retrieved evidence can include both source code and generated summaries.
- The prompt given to the local model contains the retrieved evidence.
- Irrelevant fragments are not required for a valid answer.

### US3 - Stay local and cite evidence explicitly

As a maintainer, I want the question-answer flow to stay entirely local and to
name the repository evidence it used so that the feature remains auditable and
does not leak code externally.

Acceptance criteria:

- No code data is sent to any non-local service during question answering.
- The answer names the files and symbols used as evidence.
- If the local model is unavailable, the pipeline fails clearly instead of
  falling back to another service.

## Functional Requirements

### Question answering

- The pipeline must accept a natural-language question from a developer.
- The pipeline must return a natural-language answer.
- The answer must be based on the indexed repository content.
- The answer must include explicit citations to the repository files and
  symbols that support it.

### Local retrieval

- The pipeline must find the most relevant local code fragments for the
  question.
- The pipeline must be able to use existing summaries as supporting evidence
  when they improve the answer.
- The retrieval step must prefer evidence that is directly related to the
  question instead of broad, repository-wide context.
- The pipeline must work even when the repository contains multiple languages
  or multiple files with similar names.

### Local generation

- The pipeline must send the retrieved local evidence to the configured local
  model.
- The pipeline must not send repository content to any external model or
  external service.
- The pipeline must fail clearly if the local model cannot be used.
- The pipeline must not silently substitute a different answer source.

### Citations and traceability

- The answer must name the files that were used to justify it.
- The answer must name the symbols that were used to justify it when symbol
  level evidence is available.
- The answer payload must preserve both the cited file paths and the cited
  symbol ids so the UI can render citations without parsing prose.
- The answer must remain traceable to the retrieved evidence, even when the
  final wording is concise.

### Local operation

- The pipeline must operate entirely within the local environment.
- The pipeline must not require external network access to answer a question.
- The pipeline must preserve repository confidentiality throughout retrieval and
  generation.

## Edge Cases

- If the repository does not contain enough evidence to answer the question,
  the system should say so clearly and still cite the nearest relevant files or
  symbols it found.
- If multiple fragments are similarly relevant, the system should prefer the
  most directly related evidence and mention the ambiguity when needed.
- If the question refers to a capability that appears in several files, the
  answer should cite all directly relevant locations rather than only one.
- If the local model is unavailable, the user should receive an explicit
  failure message before any answer generation begins.

## Assumptions

- The repository has already been indexed locally.
- Local embeddings and the local model are already supported elsewhere in the
  product and are reused for this pipeline.
- The repository may already contain generated summaries that can improve
  retrieval quality.
- The answer can cite both source files and symbol names when both are useful.

## Success Criteria

- For a test question such as "where is authentication handled?", the answer
  cites the correct files and functions from the test repository.
- The answer is produced using only local repository evidence and the local
  model.
- No external network request is emitted during the full retrieval and answer
  flow.
- A user can trace each substantive claim in the answer back to cited
  repository evidence.

## Key Entities

### UserQuestion

Represents the developer's natural-language query.

### RetrievedEvidence

Represents the ranked local fragments and summaries selected as context for
answer generation.

### RAGContext

Represents the assembled prompt context built from the retrieved evidence.

### CitedAnswer

Represents the final natural-language answer and its explicit file and symbol
citations.

### Citation

Represents a file or symbol reference used to justify part of the answer.
