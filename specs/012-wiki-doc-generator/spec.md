# Feature Specification: Local Wiki Documentation Generator

## Overview

Build a documentation generator that assembles, from the metadata extracted
during indexing and the summaries generated by the local AI, a structured set
of wiki-style documentation pages describing the analyzed repository: a home
page presenting the overall project architecture, one page per module
describing its role and its classes/functions with their summaries, and one
page per dependency diagram. Every page must link to the pages of related
modules and symbols so a reader can navigate the documentation like a wiki.

The generator must produce Markdown output that is versionable and committable
inside a documentation folder that stays separate from the analyzed
repository's source, with an HTML rendering also available for browsing
outside of a Markdown viewer. When the repository is re-indexed
incrementally, the generator must regenerate only the pages impacted by the
change rather than rebuilding the entire wiki.

## Goals

- Produce a home page that accurately reflects the project's real module and
  dependency architecture.
- Produce one page per module describing its role and listing its
  classes/functions with their generated summaries.
- Produce one page per dependency diagram showing how modules relate to each
  other.
- Link every page to the related module and symbol pages it references,
  enabling wiki-style navigation.
- Emit output in a versionable, committable format inside a documentation
  folder that stays separate from the analyzed source.
- Regenerate only the pages affected by an incremental re-index instead of
  the entire documentation set.

## Non-Goals

- Modifying or writing to the analyzed repository's source files.
- Automatically committing or pushing the generated documentation to version
  control on the user's behalf.
- Generating documentation content using anything other than the already
  extracted metadata and already generated local summaries (no new analysis
  or summarization logic).
- Hosting or serving the generated documentation (e.g., a live doc site with
  search); the generator only produces exportable page files.
- Translating or localizing generated documentation into multiple languages.

## User Stories

### US1 - Browse the project architecture from a home page

As a developer joining a new repository, I want a generated home page that
presents an overview of the project's architecture so that I can quickly
understand how the codebase is organized before diving into individual
modules.

Acceptance criteria:

- The home page lists the project's modules.
- The home page presents the overall architecture in a way that reflects the
  real module structure and their relationships.
- The home page links to each module's dedicated page.
- The home page links to the dependency diagram pages.

### US2 - Read a module's role, symbols, and summaries

As a developer, I want a dedicated page for each module that describes its
role and lists its classes and functions with their generated summaries so
that I can understand what a module does without reading its source code.

Acceptance criteria:

- Each module has its own page.
- The module page describes the module's role.
- The module page lists the module's classes and functions.
- Each listed class/function shows its generated summary when one exists.
- The module page links to the pages of related modules and symbols it
  references.

### US3 - Navigate dependency diagrams like a wiki

As a developer, I want dependency diagram pages that show how modules depend
on each other, with links to the related module pages, so that I can explore
the codebase's structure interactively.

Acceptance criteria:

- Each dependency diagram has its own page.
- The diagram page shows the modules involved and their dependency
  relationships.
- Each module referenced in the diagram links to its module page.
- The module page links back to the diagram page(s) that reference it, so
  navigation works in both directions.

### US4 - Regenerate only impacted pages after incremental re-indexing

As a maintainer of the documentation, I want only the pages affected by a
re-indexed change to be regenerated so that documentation updates stay fast
and the rest of the wiki remains untouched.

Acceptance criteria:

- After an incremental re-index affecting a subset of files/symbols, only the
  corresponding module pages, diagram pages, and any page whose links are
  affected are regenerated.
- Pages unaffected by the change are left unchanged.
- The home page is regenerated only when the change affects the overall
  architecture overview it presents.
- The regenerated documentation set remains fully consistent, with no
  dangling links, after a partial regeneration.

### US5 - Export versionable documentation into the analyzed repository

As a maintainer, I want the generated documentation to be written as plain
files in a separate documentation folder inside the analyzed repository so
that I can review, diff, and commit it using the same version control
workflow as the rest of the project.

Acceptance criteria:

- Generated pages are written to a documentation folder that is distinct from
  the analyzed source folders.
- The generated files are plain text-based formats (Markdown and HTML)
  suitable for diffing and committing.
- Regenerating the documentation does not modify any file outside the
  documentation folder.
- The documentation folder can be committed to version control using
  standard tools, without additional export or conversion steps.

## Functional Requirements

### Home page

- The generator must produce one home page presenting an overview of the
  project's architecture.
- The home page must list all modules discovered during indexing.
- The home page must reflect the real dependency structure among modules.
- The home page must link to every module page and every dependency diagram
  page it presents.

### Module pages

- The generator must produce one page per module.
- Each module page must describe the module's role.
- Each module page must list the module's classes and functions.
- Each module page must show the generated summary for each listed
  class/function when a summary exists.
- Each module page must link to the pages of modules and symbols it is
  related to (e.g., through dependencies or references).
- A module without a generated summary must still receive a page listing its
  structure, clearly indicating the missing summary rather than failing
  generation.

### Dependency diagram pages

- The generator must produce one page per dependency diagram.
- Each diagram page must present the modules and the dependency relationships
  between them.
- Each module shown in a diagram must link to its module page.
- Each module page must link back to the diagram page(s) that reference it.

### Wiki-style navigation and links

- Every generated page must include links to directly related module/symbol
  pages instead of only prose references.
- Links between generated pages must resolve to existing pages, with no
  broken links, after a full generation.
- Links must remain valid after a partial, incremental regeneration.

### Output format

- The generator must produce the documentation as Markdown files that can be
  versioned and committed as plain text.
- The generator must also produce an HTML rendering of the same documentation
  pages for browsing without a Markdown viewer.
- The generated output must be written into a documentation folder that is
  separate from the analyzed repository's source folders.
- The generator must not modify any file outside the documentation folder.

### Incremental regeneration

- The generator must determine which pages are impacted by a given
  incremental re-index (changed modules, changed symbols, changed dependency
  edges).
- The generator must regenerate only the impacted pages, plus any page whose
  links would otherwise become inconsistent.
- The generator must leave unaffected pages unchanged during an incremental
  regeneration.
- The generator must be able to perform a full regeneration of all pages on
  demand (e.g., first run, or explicit rebuild).

## Edge Cases

- A module with no classes or functions worth documenting should still
  receive a page describing its role, without an empty or broken symbol list.
- A symbol referenced by a module page that has since been removed from the
  repository must not produce a dangling link; the generator must update or
  remove the reference on the affected page.
- If two modules have colliding names (e.g., in different subdirectories or
  languages), the generator must give each its own page with unambiguous,
  distinct links.
- If a dependency diagram becomes empty after a change (e.g., a module loses
  all its dependencies), the corresponding diagram page must still be
  regenerated consistently rather than left stale.
- If the documentation folder already contains manually edited or unrelated
  files, the generator must only touch the files it manages and must not
  delete unrelated content it did not generate.
- If the local summaries for a module are still pending or missing, the
  module page must be generated with the available structural metadata and
  must clearly indicate that a summary is not yet available.

## Assumptions

- The repository has already been indexed, and module/symbol metadata and
  dependency information (from the existing extraction and dependency-graph
  pipelines) are available before documentation generation runs.
- Symbol summaries shown on module pages are the ones already produced by the
  existing local summary pipeline; this feature does not generate new
  summaries itself.
- "Committable and versionable" means the generator writes plain files to a
  documentation folder inside the analyzed repository; committing those files
  to version control remains a separate, user-initiated action.
- Documentation generation is triggered as an explicit step (e.g., after an
  indexing or re-indexing run), not silently on every file save.
- A "dependency diagram" corresponds to the dependency relationships already
  computed by the existing dependency-graph feature, presented at a
  granularity (e.g., per module) consistent with that existing data.
- Both the Markdown and HTML outputs are derived from the same underlying
  page content, not maintained as independently authored formats.

## Success Criteria

- On an indexed test repository, the generated home page lists the project's
  actual modules and reflects their real dependency relationships.
- Every generated module page lists the module's actual classes/functions
  along with their generated summaries when available.
- Every link on a generated page resolves to an existing page within the
  generated documentation set, with zero broken links.
- After changing a single module and re-indexing incrementally, only the
  pages impacted by that change are regenerated, and the rest of the
  documentation set remains unchanged and still fully linked.
- The full generated documentation set lives inside one separate, clearly
  identified folder within the analyzed repository and does not modify any
  source file.
- A person unfamiliar with the codebase can navigate from the home page to
  any module's classes/functions and their summaries using only the
  generated links, without consulting the source code.

## Key Entities

### DocumentationPage

Represents one generated page (home, module, or dependency diagram),
including its content sections and its outbound links to related pages.

### ModulePage

Represents the documentation page for a single module: its role description,
its listed classes/functions, and their summaries.

### DependencyDiagramPage

Represents the documentation page presenting a dependency diagram and the
module links it exposes.

### PageLink

Represents a navigable link from one generated page to another related
module or symbol page.

### DocumentationSet

Represents the full collection of generated pages written to the
documentation folder, plus the metadata needed to determine which pages are
impacted by a future incremental change.

### RegenerationImpactSet

Represents the set of pages that must be regenerated in response to a given
incremental re-index.
